# 邮箱接码服务（mail-code-service）· 需求文档

> **一句话定位**：把「高校邮箱别名 + 收码」这一单账号能力，**productize（产品化）** 成一个**可售卖、可自用**的接码服务——多账号编排、按订单（唯一码 + 前缀）访问控制、别名互斥下的租约调度、超时自动释放，对外提供 **Web 页面** 与 **HTTP API** 两种取码入口。

- **文档状态**：草案（含需你确认的关键假设，见 §14）。
- **项目性质**：**全新独立项目**，在根目录下新建目录（暂名 `mail-code-service`，最终名待定），独立 git。**与 `register-factory` 无源码耦合**。
- **与 SWPU 邮箱能力的关系**：本服务的「单账号邮箱自动化」直接构建在 `docs/swpu-email-requirements.md` 定义的能力之上（见 §0），自身只负责其上的**业务编排与产品层**。

## 0. 依赖基座：SWPU 邮箱能力（单账号）

本服务**不重新发明**单账号邮箱自动化，而是把它当作底层依赖。`swpu-email-requirements.md` 已定义的单账号能力如下，本服务直接复用：

| 能力 | 通道 | 来源 |
|---|---|---|
| 登录取凭证（cookie + zid，失效自愈、single-flight） | CloakBrowser 仅登录 | swpu-email FR-1 |
| 设置/获取别名（同一时刻仅一个别名，`action=mod`） | HTTP | swpu-email FR-2 |
| 收码（To/From/时间窗三重匹配 + IDLE/超时） | IMAP | swpu-email FR-4 |
| 删信（按 UID `STORE \Deleted` + `EXPUNGE`） | IMAP | swpu-email FR-3 |

### 0.1 抽象为 `EmailProvider` 接口（多大学可插拔）

接码服务面向**多个高校邮箱**（不同大学、不同域名）。**不同大学在「登录取凭证、重登/失效判定、改别名接口、收码通道」上均有差异**，因此把单账号能力抽象为统一接口，**把差异点显式拆成独立方法**，由各校各自实现；**调度核心只依赖本接口，永不直接触碰浏览器/HTTP/IMAP 细节**。SWPU 为首个实现：

```ts
/** 每个大学 = 一份配置 + 一个本接口实现；新增大学不改调度核心 */
interface EmailProvider {
  readonly accountId: string;            // 账号唯一标识
  readonly domain: string;               // 如 swpu.edu.cn
  readonly group: string;                // 分组（按大学/平台兼容性，套餐据此选号）

  /** 能力与规则声明：驱动别名生成、收码默认正则、是否支持 IMAP 删信等 */
  capabilities(): ProviderCaps;          // { aliasRule, receiveChannel:'imap'|'web', supportsImapDelete, ... }

  // ── A. 登录取凭证（差异最大）：浏览器自动化流程因校而异 ──
  login(): Promise<Session>;             // 表单步骤/验证码类型(图形/滑块/短信)/成功判定 各校不同；仅失效时调用
  isSessionValid(probe: unknown): boolean; // 失效信号因校而异（SWPU=_login=0 / 特定 alert 文案）
  ensureSession(): Promise<Session>;     // single-flight：有效则复用，失效则 login()

  // ── B. 别名（HTTP 路径/参数/成功判定 因校而异）──
  getCurrentAlias(): Promise<string>;
  setAlias(newAlias: string): Promise<{ ok: boolean; finalAlias: string }>; // 冲突自动加后缀

  // ── C. 收码（按需订阅：provider 在绑定租约时建 IMAP 连接，命中邮件主动回调）──
  //    交付「整封邮件」MailMeta（from/to/subject/date/text/html + uid 去重），
  //    服务端不提取验证码；由消费端自行解析（Web 用户看邮件 / 自用程序匹配）
  subscribeMail(match: MailMatch, onMail: (mail: MailMeta) => void): Unsubscribe;

  // ── D. 删信（IMAP 或网页，因校而异）──
  cleanup(criteria?): Promise<{ deleted: number }>;
}
```

> 本服务**面向接口编程**：账号池里装的是一组 `EmailProvider` 实例（**可以是不同大学的不同实现**），调度层只调接口，**与具体大学解耦**。

### 0.2 各大学差异点清单（每校必须各自实现/配置）

你提到的「登录方式、重登、改别名接口都不同」——已显式建模为下列差异点。**新增一所大学 = 填齐这张表 + 实现 `EmailProvider`，零改调度核心**：

| 差异点 | 落在接口的哪里 | SWPU 现状（参考基座） | 新校需要做的事 |
|---|---|---|---|
| **登录流程** | `login()` | 渐进表单 + 图形验证码打码，成功判定=跳转 `?q=base` | 重写表单步骤/验证码类型(图形/滑块/短信)/成功判定 |
| **会话模型** | `Session` 结构 | `{ cookies, zid, ua, headers }` | 定义本校凭证形态（cookie/token/自定义头） |
| **失效判定** | `isSessionValid()` | `_login=0` 或特定 alert 文案；探针用 `?q=base` | 给出本校的失效信号与探针 |
| **重登触发/自愈** | `ensureSession()` | single-flight 重登 + 原请求重放（封顶） | 复用同一 single-flight 骨架，替换判定 |
| **改别名接口** | `getCurrentAlias()/setAlias()` | 根路径 `/?q=settings.alias.do`，`action=mod&old=&alias=`，`res=1` | 替换路径/参数/成功判定/冲突文案 |
| **别名命名规则** | `capabilities().aliasRule` | 字符集/长度/`@swpu.edu.cn` | 给出本校字符集/长度/域名/前后缀约束 |
| **收码通道** | `subscribeMail()` | IMAP `mailgate.swpu.edu.cn:993` + 独立密码，按需订阅推送整封邮件 | 配置本校 IMAP；若不支持 IMAP 则实现网页读信 |
| **验证码格式** | 套餐 `codeRegex` / `capabilities()` | 默认 `\b\d{4,8}\b` | 按目标平台覆盖 |
| **删信方式** | `cleanup()` | IMAP `STORE \Deleted`+`EXPUNGE` | IMAP 或网页删信 |

### 0.3 新增大学的标准步骤

1. 在 `src/provider/<school>/` 实现 `EmailProvider`（可复制 swpu 实现做骨架）；
2. 填 §0.2 差异表对应的配置（登录 URL、IMAP 参数、别名接口、别名规则、正则）；
3. 在账号注册表登记该校账号并归入某 `group`；
4. 套餐（前缀）通过 `allowedGroups` 选用该校账号；
5. **调度核心 / 安全不变量 / API / 前端均无需改动**——它们只认接口。

## 1. 背景与目标

### 1.1 要解决的问题

高校邮箱「别名可改 + 能收码」的特性天然适合做**一次性、可定向的接码**。需要把它包装成：

- **可售卖**：付费用户拿到一个带唯一码的链接，打开后**点击「申请邮箱」即得一个已设好别名的邮箱地址**，拿去目标平台注册，**网页实时回显收到的整封邮件**（验证码/激活链接由用户自行查看）。
- **可自用**：我自己批量注册账号时，通过 **HTTP API** 申请别名、取整封邮件（自己的程序解析验证码）。

### 1.2 核心特性

| 特性 | 说明 |
|---|---|
| **按订单定向** | 唯一码带**前缀**，前缀决定「能用哪组邮箱、收谁的码、配额、有效期」（如 `gh-` 仅用于 GitHub、仅限某域名邮箱）。 |
| **一次性隔离** | 每次取码独占一个邮箱别名；用完即释放，互不串号。 |
| **超时自动释放** | 给出邮箱后 **15 分钟**（可配）内未收到码 → 自动释放；只要未成功收码，用户可重新申请。 |
| **两种入口** | Web（人）+ API（机器），共用同一调度核心。 |

> **规模假设与设计取向（决定实现风格）**：账号数少（**≤3**）、售卖分散、**并发取码极少发生**。因此首版**以正确性与健壮性为最高优先，吞吐不是目标**：
> - **头号目标：杜绝「一个唯一码取得多个验证码」**（详见 §6 FR-0 的不变量与并发控制）。
> - **以「串行化」换「绝对正确」**：所有关键状态变更（创建租约 / 收码交付 / 扣配额 / 超时 / 释放 / 重申请）经**单写串行执行**（单进程 + SQLite 单写事务），低并发下零成本却根除竞态（C-7）。
> - 排队（§6 FR-3.8）作为正确性兜底保留，**实际几乎不触发**，不为其做任何性能优化。

### 1.3 非目标（首版不做）

- 不做支付/计费对接：唯一码**由管理员预先批量生成/发放**，支付在本系统之外完成。
- 不做发信（SMTP）。
- 不改动 `register-factory` 任何文件。
- 不实现各业务平台的注册主流程（那是唯一码的购买者/或 `register-factory` 自己的事）。

## 2. 核心概念与术语

| 术语 | 英文/标识 | 含义 |
|---|---|---|
| 邮箱账号 | **EmailAccount** | 一个真实高校邮箱（一个 `EmailProvider` 实例），是接码的**最小资源单位**。 |
| 账号分组 | **Group** | 按大学/域名/可用性对账号分组，套餐据此限定可用账号。 |
| 别名 | **Alias** | 账号当前生效的收件地址（`<alias>@<domain>`）。**每账号同一时刻仅一个**。 |
| 套餐（前缀） | **Plan / Prefix** | 唯一码前缀对应的一套约束：允许的账号分组、目标发件人、取码正则、配额、TTL。 |
| 唯一码 | **AccessCode** | 售卖/自用的访问凭证（`<prefix>-<random>`），是用户进入服务的 bearer token。 |
| 租约 | **Lease** | 一次「占用某账号 + 设别名 + 等码」的会话，是调度与超时的核心实体。 |
| 配额 | **Quota** | 一个唯一码允许的**成功收码次数**（默认 1）。 |
| 收码 | **Receive** | 经 IMAP 命中一封匹配邮件（To=别名 + From=目标 + 时间窗）后，**把整封邮件原文交付**给取码方的过程。**服务端不提取验证码**——验证码由用户（Web）自行从邮件查看、或由自用方（API）自己的程序解析。 |

## 5. 关键约束（决定设计上限）

- **C-1 别名互斥 → 账号内串行**：每账号同一时刻仅一个别名，故一个账号的生命周期是 `setAlias → 等码/超时 → 释放 → 下一个`，**不可并行复用同一账号**。
- **C-2 并发容量 = 可用账号数**：某套餐的并发取码上限 = 其允许分组内**空闲账号数**。**跨账号并行、账号内串行**。扩容=加账号。
- **C-3 别名全局唯一**：别名即邮箱地址，全域唯一。生成需防碰撞，冲突自动加后缀重试（委托 provider，见 swpu FR-2.3）。
- **C-4 收码三重匹配防串号**：`To=本租约别名` + `From=套餐目标发件人` + `since=本次 setAlias 时间`，再辅以 `UNSEEN`。**绝不能**把上一个租约的残留邮件当成本次的码。
- **C-5 浏览器只登录**：常态走 HTTP（别名）+ IMAP（收码/删信）；仅会话失效时临时拉起 CloakBrowser（委托 swpu-session，single-flight）。
- **C-6 状态须持久化**：账号占用、租约、唯一码配额必须落盘，**进程重启后可恢复**（恢复占用关系、为 active 租约按需重连 IMAP、继续/超时未决租约）。
- **C-7 有状态单实例**：服务本质有状态——活跃租约的按需 IMAP 连接、账号互斥锁、PENDING 队列、租约超时定时器、SSE 推送均为**进程内内存态**，必须由**唯一进程**持有；且并发容量由账号数决定（C-2），**横向扩展不增容量反引入双占风险**。故**首版按单实例部署**，调度依赖进程内内存，不引入 Redis（理由与边界见 §10.5）。

## 6. 功能需求

### FR-0 头号安全不变量：杜绝「一码多码」（贯穿所有功能，最高优先级）

> **一句话**：一个唯一码（在其配额内）**有且仅有**约定次数（默认 1）的成功收码；任何并发、刷新、重申请、超时、迟到邮件、进程重启都不得突破。下列不变量由 **数据库约束 + 单写串行事务** 双重保证，**不依赖应用层自觉**。

#### FR-0.1 核心不变量（须可断言、可测试）

| 编号 | 不变量 | 强制手段 |
|---|---|---|
| **INV-1** | 任一时刻，一个 `accessCode` **至多一个 `ACTIVE` 租约** | DB partial unique index |
| **INV-2** | 任一时刻，一个 `account` **至多一个 `ACTIVE` 租约** | DB partial unique index |
| **INV-3** | 配额扣减是**原子条件更新**，**仅在租约 `ACTIVE→RECEIVED` 的唯一一次转换时**发生；`quota_left` 永不为负 | 条件 `UPDATE ... WHERE quota_left>0` + 校验 affected 行数 |
| **INV-4** | 终态（`RECEIVED/EXPIRED/CANCELLED/REJECTED`）**不可逆**；**非 `ACTIVE` 租约绝不交付码、绝不扣配额** | 状态机 + 条件 `WHERE status='active'` |
| **INV-5** | **「码交付」与「扣配额」在同一事务内原子完成**——要么都成功要么都不 | 单事务包裹两条 UPDATE |
| **INV-6** | 一切「读—判断—写」收敛为 **DB 原子操作** 或 **单飞锁内串行**，无 TOCTOU | 单写串行执行器 + 内存单飞锁 |

#### FR-0.2 实现机制

- **M1 单写串行执行器**：所有状态变更（createLease / 收码交付 / 超时 / release / renew）经**单一串行队列**提交，单进程内天生串行（C-7）。低并发下无性能损失，却消除竞态。
- **M2 数据库护栏（partial unique index）**：即便代码有 bug，DB 也会**直接拒绝**第二个活跃租约：
  ```sql
  CREATE UNIQUE INDEX uq_active_lease_per_code
    ON lease(access_code) WHERE status = 'active';
  CREATE UNIQUE INDEX uq_active_lease_per_account
    ON lease(account_id)  WHERE status = 'active';
  ```
- **M3 收码交付的原子事务（INV-3/4/5 的落地）**——封堵「一码多码」的核心。**交付物是整封邮件**（存 `mail_uid` + `mail_meta`，不在此提取验证码）：
  ```sql
  BEGIN IMMEDIATE;
    -- ① 仅当租约仍 ACTIVE 才推进（拦重复投递/已超时/已取消）
    UPDATE lease SET status='received', mail_uid=:uid, mail_meta=:mailJson
      WHERE id=:leaseId AND status='active';
    -- affected=0 → 该租约已非 active（超时/取消/被别的邮件先交付）→ ROLLBACK，丢弃此邮件
    -- ② 同一事务内扣配额；affected 必须=1
    UPDATE access_code SET quota_left = quota_left - 1
      WHERE code=:accessCode AND quota_left > 0;
    -- 若 ②affected=0（配额已耗尽却还在交付）→ 视为严重不一致，ROLLBACK + 告警
  COMMIT;  -- 仅当①②都 affected=1 才提交；邮件对用户的"交付"以本事务 COMMIT 为准
  ```
  > **关键**：用户拿到邮件 = 本事务 COMMIT 的副产物。两条 UPDATE 任一失败即整体回滚，**绝不会出现「邮件已交付但配额没扣」或「配额扣了邮件没交付」**。
- **M4 activate/renew 单飞锁**：按 `accessCode` 加进程内单飞锁，**同码并发 activate 共享同一次结果**（复用同一租约），不会各开一个租约（配合 INV-1 双保险）。
- **M5 收码幂等**：按 `(accountId, mailUid)` 记录已处理邮件，**同一封邮件二次进入直接丢弃**，杜绝重复交付。
- **M6 状态机不可逆**：租约状态只能 `PENDING→ACTIVE→{RECEIVED|EXPIRED|CANCELLED}` / `PENDING→REJECTED` 单向流转；任何把终态改回 ACTIVE 的尝试被拒。

#### FR-0.3 威胁路径与封堵（逐条）

| # | 可能导致「一码多码」的路径 | 封堵 |
|---|---|---|
| A | 同码并发两次 `activate`，各开一租约各收一码 | M4 单飞锁 + INV-1（DB index） |
| B | 两封邮件几乎同时命中，配额各扣一次（TOCTOU） | M3 原子条件 UPDATE（quota 只会被扣到 0） |
| C | 超时**重申请**后，**旧别名迟到收到码**，旧租约又交付 | INV-4：旧租约已是终态 → M3 的①affected=0 → 丢弃 |
| D | 码已用尽（quota=0）后再次 `activate` | **不新建租约**：保留期内返回只读回看（FR-2.7），过期返回 `CODE_EXPIRED`；**配额不再消费**，故不会多码 |
| E | 一个账号被两个租约同时占用，两个码都进来 | INV-2（DB index）+ M1 串行 acquire |
| F | 同一封邮件被 IMAP 事件触发两次 → 交付两次 | M5 幂等 + M3 的①（第二次 affected=0） |
| G | 进程重启后把已 RECEIVED 租约误当 ACTIVE 继续收码 | 状态落盘；恢复时以 DB 为准，终态不复活（INV-4） |
| H | `renew` 时旧 ACTIVE 租约未关，出现两个 ACTIVE | renew 须**先原子置旧租约终态再建新**；INV-1 兜底 |

#### FR-0.4 「使用」与配额的唯一定义

- **「使用掉」⇔ 成功收码一次（`RECEIVED`）⇔ `quota_left` 减 1**。这里**「成功收码」= 收到并交付一封匹配邮件（To+From+时间窗命中）**，与能否从中提取出验证码无关。**超时 / 取消 / 重申请 / 排队失败一律不扣**（FR-2.5）。
- `quota_left` 归零 → 唯一码 `used`；**保留期（`retainUntil`，默认 7 天）内**再次 `activate` 返回**只读回看**（FR-2.7），**不新建租约、不再消费配额**（故不破坏本不变量）；超保留期 → `expired`，提示「无效的唯一码」。

### FR-1 账号池管理（AccountPool）

- **FR-1.1 账号注册表**：每账号含 `{ id, university, domain, group, status, imap 凭证引用, 会话引用, currentAlias, lastError, disabled }`。凭证只存引用/密钥库，**不落明文**（NFR-1）。
- **FR-1.2 健康状态**：`free | leased | reloging | unhealthy | disabled`。IMAP 断连或登录连续失败 → `unhealthy`，暂不参与分配；自愈成功后恢复 `free`。
- **FR-1.3 空闲选取**：`acquire(group)` 原子地从该分组挑一个 `free` 账号置 `leased`（加锁，杜绝并发双占，NFR-3）。
- **FR-1.4 释放**：`release(accountId)` 把账号置回 `free`，记录本次租约结果；可选**冷却期**（释放后 N 秒再可分配，给 IMAP/别名状态稳定时间）。
- **FR-1.5 启动预热**：启动时按 §C-6 从 Store 恢复占用关系、加载持久化会话（命中则免开浏览器）；**IMAP 不在启动时常驻**，改由租约绑定时按需建连（FR-4.1）；重启恢复对 active 未过期租约即时重连 IMAP（§3.5）。

### FR-2 套餐 / 前缀 / 唯一码（Plan & AccessCode）

- **FR-2.1 套餐模型**：`Plan { prefix, name, allowedGroups[], targetSenders[], codeRegex, quota=1, leaseTtlSec=900, retentionSec（默认 7 天）, maxRenews }`。`prefix` 唯一，决定唯一码归属与全部约束。
- **FR-2.2 唯一码模型**：`AccessCode { code=<prefix>-<random≥128bit>, plan, status, quotaLeft, issuedAt, retainUntil?, boundLeaseId? }`。
  - `status` 生命周期：`unused`（未激活，**永久有效、永不过期**）→ `active`（收码中）→ `used`（已成功收码、**结果回看期内**）→ `expired`（**无效**，仅因回看期满产生）；另有 `revoked`（管理员吊销）。
  - **未使用的码一直保留**，不设激活期限；`retainUntil` 仅在**首次成功收码后**才赋值。
  - `retainUntil = 最后一次成功收码时间 + retentionSec（默认 7 天）`：**收码结果保留窗口**，期内可回看，超期作废为 `expired`。
- **FR-2.3 批量生成**：管理员按套餐批量生成唯一码（指定数量/有效期），导出供售卖发放。
- **FR-2.4 校验与分流**：激活时——`unused/active` 且 `quotaLeft>0` → 正常建/复用租约（**`unused` 永久有效，不论签发多久**）；**`used` 且 `now ≤ retainUntil` → 只读回看历史收码（FR-2.7，不建租约、不扣配额）**；`expired`（超 `retainUntil`）→ `CODE_EXPIRED`「无效的唯一码」；`revoked`/前缀停用 → 对应错误码（见 §9）。
- **FR-2.5 配额语义**：**仅成功收码 (`RECEIVED`) 才扣减 `quotaLeft`**；超时/取消/重申请**不扣**。`quotaLeft` 归零 → `used`。
- **FR-2.6 单活跃租约**：一个唯一码同一时刻最多一个**活跃租约**，避免一码多占。
- **FR-2.7 收码结果回看（`used` 态只读）**：已成功收码的唯一码在 `retainUntil` 之前再次进入，**不新建租约、不再消费配额**，返回**只读历史邮件**——每条成功收码的整封邮件 `{ alias, from, to, subject, receivedAt, text, html, code? }`（`quota>1` 时为多条）。让用户回看已收到的邮件原文（`code` 仅为可选的便利提取字段）。
- **FR-2.8 保留与失效（默认 7 天）**：
  - **未使用的码永久保留**（`unused` 永不过期），仅在被 `revoked` 或被使用后才改变状态。
  - 收码结果自**最后一次成功收码起保留 `retentionSec`（默认 7 天）**；窗口内可回看（FR-2.7）。
  - 超过 `retainUntil` → 置 `expired`，关联收码详情交由 GC 清理（FR-10）；此后进入提示「**无效的唯一码**」（`CODE_EXPIRED`）。

### FR-3 租约调度（LeaseManager）— 核心

- **FR-3.1 租约模型**：`Lease { id, accessCode, accountId, alias, status, startTime, expiresAt, mailMeta?, code?, renews }`。状态机：

  ```
  PENDING ──(分到账号)──▶ ACTIVE ──(收到邮件)─▶ RECEIVED   ✅终态(扣配额)
     │  排队等待空闲账号      │  setAlias完成        │
     │                       ├──(15min无邮件)▶ EXPIRED   ⏱终态(释放，配额不扣)
     └──(等待超时无账号)─▶ REJECTED              │
                              └──(用户/API取消)─▶ CANCELLED
  ```
- **FR-3.2 申请租约 `createLease(accessCode)`**：
  1. 经 FR-2.4 校验唯一码；
  2. `AccountPool.acquire(plan.allowedGroups)` 取空闲账号；无空闲则**建 `pending` 租约入队并立即返回**（前端显示排队位次与已等待时长）；账号释放时按分组 FIFO 自动 `promote` 为 `active`；超 `queueTimeout`（兜底，默认 30min）仍未轮到才 `REJECTED`；
  3. 拿到账号 → `provider.setAlias(生成的唯一别名)`（冲突自动加后缀）→ 记 `startTime`、`expiresAt=now+leaseTtlSec` → 置 `ACTIVE`；
  4. ReceiverHub 把该账号的收码绑定到本租约；
  5. 返回 `{ leaseId, alias, expiresAt }`。
- **FR-3.3 别名生成**：随机/可读策略（参考 `register-factory` 的 alias-generator 思路，但独立实现），保证**域内唯一**与**与目标平台兼容**（长度/字符集）。
- **FR-3.4 超时释放**：到 `expiresAt` 仍 `ACTIVE` → `EXPIRED` → `AccountPool.release` → 解绑收码。**配额不扣**。
- **FR-3.5 重申请 `renewLease`**：唯一码在 `quotaLeft>0` 且当前租约为 `EXPIRED/CANCELLED/REJECTED` 时，可再次 `createLease`（计 `renews`，受 `plan.maxRenews` 限制）。**可能分到不同账号、不同别名**。
- **FR-3.6 提前释放**：API/页面可主动 `cancel`，立即释放账号。
- **FR-3.7 公平与防饿死**：PENDING 队列 FIFO；空闲账号到来按队列顺序分配。同一套餐/分组维度各自一条等待队列（不同分组互不阻塞）。
- **FR-3.8 排队（异步 pending 队列）**：池满 → 建 `pending` 租约入队并立即返回 `{status:"pending", queueAhead, enqueuedAt}` → 账号释放时按分组 FIFO **自动 `promote`**（真实 setAlias）为 `active`。前端展示**「前面还有几人」（`queueAhead`）** 与**「已排队多长时间」**（按 `enqueuedAt` 本地计时）。**`etaSec` 预计等待不做**（账号 ≤3、样本小，预估不准反误导）。排队**不设产品硬超时**，仅 `queueTimeout`（默认 30min）兜底防泄漏。同码并发/刷新复用同一 `pending`（INV-1′，配合 DB 护栏 `uq_pending_lease_per_code`）。

### FR-4 收码集成（ReceiverHub）

> **交付物 = 整封邮件，不是验证码**：服务端命中匹配邮件后，**把整封邮件原文（发件人/主题/时间/正文 text+html）交付**给取码方。**不在服务端做「提取验证码」这件易错的事**——Web 用户自己从邮件里看码/点激活链接，自用方由自己的程序解析（很多平台发的是激活链接而非数字码，发整封邮件可全覆盖）。`plan.codeRegex` 降级为**可选便利字段**：能抽到就附带一个 `code` 方便填表，抽不到也照常交付整封邮件，**不影响成功判定**。

- **FR-4.1 按需连接（推模型）**：IMAP **不常驻**——ReceiverHub 在租约 `setAlias` 成功后**按需建** IMAP 连接（`mailgate.<domain>:993` 隐式 TLS），IDLE 监听 `exists`，**租约存活期内**断线指数退避重连；**收码/超时/取消即断连**。**收码是「长期挂起等外部事件」**（用户拿到别名后人工去平台操作，可能等十几分钟），故连接在租约期内常驻监听、命中邮件**主动推**给当前活跃租约（`provider.subscribeMail`），而非一次性阻塞等待。
  - **连接生命周期串行化**：每账号的 `start`/`stop` 经串行链 + 连接代际（epoch）管理，反复建/断不互相破坏（旧代连接的 `exists`/重连一律失效），根除「释放后台断连 vs 下一租约新建连」竞态。
  - **建连失败即回滚**：`setAlias` 已成功但按需建连失败 → 释放账号、租约 `active→cancelled`、唯一码退回 `unused` 可重申请、返回 `RECEIVER_UNAVAILABLE`，**绝不留下「有别名却收不到码」的 active 租约**。
- **FR-4.2 路由**：因 C-1 每账号至多一个 `ACTIVE` 租约，新邮件按 §C-4 匹配命中后，**喂给该账号当前活跃租约**。
- **FR-4.3 邮件交付**：命中一封匹配邮件即视为**成功收码** → 租约置 `RECEIVED`、回填整封 `mailMeta`（`from/to/subject/date/text/html`）、扣配额、释放账号、（实时）推送给取码方。可选地用 `plan.codeRegex`（默认 `/\b(\d{4,8})\b/`）**尽力**抽一个 `code` 作便利字段一并返回，抽取失败不影响交付。先锁邮件再处理。
- **FR-4.4 匹配与时序保护**：以 **`To=本租约别名`**（一次性、全域唯一）为主隔离，叠加 **`From` 命中目标发件人** 与 **时间窗**。**发件人按域名/通配匹配**（如 `@github.com`、`*.sendgrid.net`），不写死单一地址——大量平台借第三方 ESP 代发、发件地址带动态前缀。时间窗除 IMAP `SINCE`（仅精确到「天」）外，**客户端再按邮件 `INTERNALDATE/Date` 做秒级 `≥ startTime` 精筛**，杜绝把别名复用前的历史邮件误算入本次。
- **FR-4.5 收码不删信**：删信由 FR-9 独立定时任务负责（与 swpu FR-4.6 一致）。

### FR-5 超时、释放与重申请（产品规则）

- **FR-5.1** 给出别名后 `leaseTtlSec`（默认 900s/15min）无码 → 自动 `EXPIRED` 并释放。
- **FR-5.2** 唯一码**未成功收码**（`quotaLeft` 未变）即视为「未使用」，允许 `renewLease`（FR-3.5），直至成功或耗尽 `maxRenews`。
- **FR-5.3** 倒计时与状态对前端/调用方可见（剩余秒数、是否可重申请）。

### FR-6 Web 前端（React）

- **FR-6.1 入口**：`/{code}`（或 `/r/:code`）。加载时**仅把唯一码预填/绑定到页面，不自动占用邮箱**；用户**点击「申请邮箱」按钮**才调 `activate` 创建租约。如此可避免链接被分享/预览时白白占用稀缺账号（≤3 个）。
- **FR-6.2 展示**：别名邮箱（**一键复制**）、目标平台说明（来自套餐）、**15:00 倒计时**、状态条（申请中/等待邮件/已收到/已超时）。
- **FR-6.3 实时回显**：优先 **SSE**（`/leases/:id/stream`），收到邮件即**展示整封邮件**（发件人/主题/正文，可复制）；若能尽力抽到验证码，则额外高亮一个便利字段方便复制。SSE 不可用回退轮询。
- **FR-6.4 异常态**：前缀无效/已用尽/已过期/池满（REJECTED）各有清晰文案与可操作项。
- **FR-6.5 重申请**：`EXPIRED` 后显示「重新获取邮箱」按钮（FR-3.5）。
- **FR-6.6** 仅暴露与该唯一码相关信息，**不泄露**账号真实地址、池规模、其它订单。
- **FR-6.7 SSE 终态收尾**：`received/expired/cancelled` 为流终态——服务端推一条 `done`（带最终状态/整封邮件）后 `end()`；前端收 `done` 主动 `es.close()`，不再重连。对已结束租约的重连请求回 **204** 使其彻底停止。
- **FR-6.8 单活跃订阅（首版极简）**：同一唯一码刷新/多开标签时，**新 SSE 连接一建立就关掉该码的旧连接**（服务端按 `accessCode` 只留最新一条），保证不重复推送。**正确性不依赖它**——真正防「一码多码」靠 FR-0 的 DB 护栏与单活跃租约。`seq` 单调防乒乓、`superseded` 事件、close 时校验 seq 那整套**列为 v2**，首版无需实现。全程进程内内存完成（C-7）。
- **FR-6.9 回看视图（`used` 态）**：保留期内进入已收码的唯一码，展示**历史邮件原文（只读）**与剩余保留时间（距 `retainUntil`）；超保留期展示「**无效的唯一码**」。未使用的码永久有效，进入即正常分配。

### FR-7 自用 API（programmatic）

- **FR-7.1 鉴权**：`X-API-Key`（内部密钥），与公开 `code` 入口隔离。
- **FR-7.2 申请**：`POST /api/v1/leases { plan? }` → `{ leaseId, alias, expiresAt }`（自用可直接按套餐取，不必走唯一码）。
- **FR-7.3 取码**：`GET /api/v1/leases/:id` 轮询，或 `POST` 时带 `callbackUrl` **webhook** 回调。**返回/回调的是整封邮件**（`mail: {from,to,subject,date,text,html}`），由自用方自己的程序解析所需验证码；服务端可选附带便利字段 `code`。webhook 建议带 **HMAC 签名 + 重试/超时 + 按 `leaseId` 幂等**。
- **FR-7.4 释放**：`DELETE /api/v1/leases/:id` 提前释放。
- **FR-7.5** 与 `register-factory` 集成友好：返回结构稳定、错误码明确、支持并发（受 C-2 容量约束自动排队）。

### FR-8 管理后台（Admin）

- **FR-8.1 账号**：增删改查、启用/禁用、查看健康与最近错误、**强制重登**、查看 `currentAlias`。
- **FR-8.2 套餐/前缀**：维护 `Plan`（允许分组、目标发件人、正则、配额、TTL）。
- **FR-8.3 唯一码**：批量生成、查询状态、吊销（`revoked`）、导出。
- **FR-8.4 监控面板**：池水位（free/leased/unhealthy）、实时排队数、**收码成功率 / 平均收码时延 / 超时率**、近段租约流水。
- **FR-8.5 鉴权**：Admin 独立账号体系，与公开/自用入口隔离。

### FR-9 删信清理（Cleaner，复用 swpu FR-3）

- **FR-9.1** 独立定时任务，按 IMAP `search`（已读/过期/指定发件人）取 **UID**，`messageDelete`（`STORE \Deleted`+`EXPUNGE`）批量清理。
- **FR-9.2** 与收码**解耦**：独立连接或错开收码窗口；EXPUNGE 仅作用于选中 UID，不影响活跃租约（C-1/C-4 仍成立）。

### FR-10 收码结果保留与清理（默认 7 天 GC）

> **定位**：与 FR-9「删邮件」是两件事——FR-10 清理的是**业务数据库记录**（唯一码/租约/收码详情），FR-9 清理的是**邮箱里的邮件**。可同一调度但独立执行。

- **FR-10.1 保留**：成功收码详情（`lease.code/mail_meta` 等）自**最后一次收码起保留 `retentionSec`（默认 7 天）**，期间支持只读回看（FR-2.7/FR-6.9）。
- **FR-10.2 过期作废**：定时任务把 `retainUntil < now`（已收码、回看期满）的唯一码置 `expired`。**未使用的码（`unused`）不在清理范围，永久保留**。
- **FR-10.3 物理清理**：对 `expired` 的码及其关联 `lease` / 收码详情 / `processed_mail` 做物理删除（可保留 `audit_log` 脱敏摘要用于统计）。**清理前校验无活跃租约**，绝不影响 `active` 数据。
- **FR-10.4 幂等与安全**：清理可重复执行无副作用；删除操作走事务，失败可重试。

## 7. 关键时序

### 7.1 付费用户 Web 取码（典型）

```
打开 /{code}（仅预填唯一码，不占邮箱）
  └─▶ 用户点「申请邮箱」 → activate: 校验唯一码(前缀/配额/有效期)
        └─▶ acquire 空闲账号(允许分组)  ──无空闲──▶ 排队≤60s ──仍无──▶ REJECTED(稍后再来)
              └─▶ setAlias(唯一别名)  [HTTP, 失效则自愈重登]
                    └─▶ 返回别名 + expiresAt(now+15min) → 页面显示 + 倒计时 + SSE 订阅
                          └─▶ IMAP 命中(To=别名 & From=目标 & 时间窗)
                                └─▶ 交付整封邮件 → RECEIVED → 扣配额 → 释放账号 → SSE 推送邮件
                          └─(15min 无邮件)─▶ EXPIRED → 释放 → 页面提示「重新获取」
```

### 7.2 自用 API 取码

```
POST /api/v1/leases {plan}  → {leaseId, alias, expiresAt}
  ├─ 轮询 GET /api/v1/leases/:id 直至 mail 或 expired（自用程序自行匹配验证码）
  └─ 或 webhook：收到邮件后回调 callbackUrl（带整封邮件）
```

### 7.3 超时释放与重申请

```
ACTIVE ──15min无码──▶ EXPIRED ──release──▶ 账号回 free
唯一码 quotaLeft 未变 → 用户点「重新获取」/API 再 createLease → 新租约(可能新账号/新别名)
```

### 7.4 账号会话失效自愈（委托 swpu-session）

```
别名 HTTP 返回 _login≠1 → SwpuSession single-flight 重登 → 重放原请求(封顶) → 期间该账号其它请求共享同一登录
```

### 7.5 已收码的唯一码再次进入（回看，保留期内）

```
打开 /{code} → 点「申请邮箱」/activate 命中 status=used 且 now ≤ retainUntil
  → 不新建租约、不消费配额
  → 返回历史邮件（别名/发件人/主题/正文/时间，含可选便利码）只读展示 + 剩余保留时间
（now > retainUntil → expired → 提示"无效的唯一码"，数据被 GC 清理；**未使用的码永久有效、永不过期**）
```

## 8. 数据模型（建议落 SQLite，重启可恢复）

| 表 | 关键字段 |
|---|---|
| `email_account` | id, university, domain, group, status, creds_ref, current_alias, last_error, disabled, updated_at |
| `plan` | prefix(PK), name, allowed_groups, target_senders, code_regex, quota, lease_ttl_sec, retention_sec, max_renews, enabled |
| `access_code` | code(PK), prefix→plan, status, **quota_left（CHECK ≥ 0）**, issued_at, **retain_until（NULL=未使用，永久保留）**, bound_lease_id |
| `lease` | id(PK), access_code?, plan, account_id, alias, status, start_time, expires_at, **mail_uid**, **mail_meta（整封邮件 from/to/subject/date/text/html）**, code?（可选便利提取）, renews, created_at |

**DB 层护栏（即便应用有 bug 也兜底，对应 FR-0）**：
```sql
PRAGMA journal_mode = WAL;                 -- 读写不互锁
-- 同一码 / 同一账号 至多一个活跃租约（INV-1 / INV-2）
CREATE UNIQUE INDEX uq_active_lease_per_code    ON lease(access_code) WHERE status='active';

-- 配额永不为负（INV-3）；收码幂等（M5）
-- access_code.quota_left 列加 CHECK(quota_left >= 0)
-- processed_mail 主键 (account_id, uid) 拦重复邮件
```

## 9. API 规格（REST + SSE）

**公开（凭唯一码，无需 API Key）**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/public/activate` | body `{ code }` → 分流：**有空闲账号** `{ status:"active", leaseId, alias, expiresAt, plan }`；**需排队** `{ status:"pending", leaseId, queueAhead, enqueuedAt }`；**已收码(保留期内)** `{ status:"used", results:[...], retainUntil }`（只读回看，含整封邮件）；**已失效** `CODE_EXPIRED`。（注：由 FR-6.1，Web 端是用户点「申请邮箱」才调本接口） |
| GET | `/api/public/leases/:id` | 查询租约状态：`pending`（在排队）；`active` 含 `alias/expiresAt`；`received` 含整封 `mail`（及可选便利 `code`） |
| GET | `/api/public/leases/:id/stream` | **SSE** 实时推送状态/邮件；事件类型：`message`(状态更新)、`done`(终态收尾，附整封邮件)。同一 `code` 新连接建立时关掉旧连接即可（FR-6.8 首版极简） |
| POST | `/api/public/leases/:id/renew` | 超时后重申请（受 `maxRenews`） |
| POST | `/api/public/leases/:id/cancel` | 提前释放 |
| GET | `/api/public/codes/:code/results` | **收码结果回看**：返回该码全部成功收码的整封邮件 `{ results:[{alias,from,to,subject,receivedAt,text,html,code?}], retainUntil }`；仅保留期内有效，过期返回 `CODE_EXPIRED` |

> **排队语义**：`activate` 不因池满立即失败，而是落入所属分组 FIFO 队列、建 `pending` 租约并返回 `status:"pending"`（含 `queueAhead` 前面人数、`enqueuedAt` 入队时刻）；账号释放时自动 `promote` 为 `active` 下发别名。SSE 持续推送排队进度（`queueAhead` 变化）。**`etaSec` 预计等待不做**；不设产品硬超时，`queueTimeout`（默认 30min）兜底转 `rejected`（见 FR-3.8）。

> **幂等/单飞语义（防一码多码，对应 FR-0 M4/INV-1）**：同一 `code` 并发 `activate` 或刷新页面，**复用同一个活跃租约**（按 `accessCode` 单飞），**绝不新开第二个租约**；已 `RECEIVED`/`used` 的码再 `activate` 直接返回 `CODE_EXHAUSTED`。`renew` 仅在当前租约为终态且 `quotaLeft>0` 时放行。

**自用（`X-API-Key`）**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/leases` | `{ plan?, callbackUrl? }` → `{ leaseId, alias, expiresAt }` |
| GET | `/api/v1/leases/:id` | 状态 + 整封邮件 `mail`（自用方自己的程序从中解析所需验证码；服务端可选附便利 `code`） |
| DELETE | `/api/v1/leases/:id` | 提前释放 |

**Admin（独立鉴权）**：`/api/admin/accounts`、`/plans`、`/codes`（批量生成/吊销/导出）、`/stats`。

**统一错误码**（示例）：`CODE_NOT_FOUND` / `CODE_EXPIRED` / `CODE_EXHAUSTED` / `POOL_BUSY` / `RECEIVER_UNAVAILABLE`（收码通道按需建连失败，回滚后返回） / `LEASE_NOT_FOUND` / `RENEW_LIMIT`。响应沿用 `{ errCode, errMsg, data }` 风格，便于自用端统一处理。

## 10. 非功能需求

- **NFR-1 安全**：日志严禁明文密码/cookie/IMAP 独立密码；唯一码 ≥128bit 随机、不可枚举；`.env`、`data/` 不入库。
- **NFR-2 隔离与最小暴露**：公开入口只见自己订单；不泄露账号真实地址、池规模、他人租约。前缀实现**业务定向**（套餐只能用指定分组邮箱）。
- **NFR-3 并发正确性**：`acquire/release` 原子加锁，杜绝同账号双占；唯一码「单活跃租约」「仅成功扣配额」严格成立。
- **NFR-4 限流防滥用**：按唯一码/IP 限流 activate；`maxRenews` 防无限占用。
- **NFR-5 可恢复**：满足 C-6——重启恢复占用、为 active 租约按需重连 IMAP、超时巡检续跑。
- **NFR-6 可观测**：结构化日志 + 指标（池 free/busy/unhealthy、排队数、成功率、平均收码时延、超时率）。
- **NFR-7 语言**：日志与错误信息**中文优先**。
- **NFR-8 反风控一致性**：别名 HTTP 复刻登录浏览器的 cookie/UA/关键头（沿用 swpu NFR-6，默认 L1）。
- **NFR-9 部署形态**：**单实例有状态服务**（C-7）。容器内常驻调度核心，IMAP 按需连（仅活跃租约期内）；优雅停机（SIGTERM）需先停止接收新 activate、持久化在途租约、关闭 IMAP 连接再退出。

### 10.5 部署与扩展模型（Docker / 是否 Redis）

**结论：首版单容器单实例，不引入 Redis。**

| 关注点 | 决策 | 理由 |
|---|---|---|
| 进程数 | **单实例** | 容量=账号数（C-2），多实例不增容量；IMAP 连接（按需）、账号锁、队列必须单进程持有（C-7） |
| 队列 / 锁 / 定时器 | **进程内内存** | 单进程内强一致，无需分布式协调 |
| 持久化 | **SQLite 文件**（挂 Docker volume） | 重启恢复占用/租约/配额（C-6），零运维 |
| SSE 推送 | **进程内事件** | 单实例下无需 pub/sub |
| 缓存/Redis | **暂不需要** | 无跨进程共享状态；引入只增运维成本 |

**何时才升级到 Redis（保留路径，不在首版）**：
- 把「接入层（API/Web/SSE）」与「调度核心」拆成**多进程** → Redis 做跨进程队列 + pub/sub（SSE 扇出）+ 分布式锁；
- 真要**多实例**并把账号**分片**到不同实例时 → Redis/一致性协调登记账号归属。

**预留替换点**：调度核心对外只依赖 `QueuePort`（入队/出队/查位次）与 `LockPort`（账号互斥）两个接口，首版为内存实现，将来换 Redis 实现**不改业务逻辑**。

**Docker 部署要点**：
- `data/`（SQLite + 会话缓存）必须挂 **named volume**，勿留在容器可写层，否则重启丢状态；
- CloakBrowser 二进制较大：构建阶段 `npx cloakbrowser install` 预置，运行阶段 `CLOAKBROWSER_BINARY_PATH` 固定、`CLOAKBROWSER_AUTO_UPDATE=false`（参考 cloakbrowser 文档 §8.7），避免运行时触网下载；
- 容器需 `--init` 或 tini 回收 Chromium 子进程；登录用有头模式时配 `Xvfb`（参考 cloakbrowser 文档 §10.3）；
- 健康检查暴露 `/healthz`（含池水位、IMAP 连接数）。

## 12. 验收标准

1. **多账号并发 + 排队**：N 个账号支持 N 个并发取码；第 N+1 个请求进入**所属分组 FIFO 队列**（`status=pending`，返回 `queueAhead` 位次与 `enqueuedAt`），账号释放时自动 `promote` 为 `active` 下发别名；超 `queueTimeout`（默认 30min 兜底）才 `rejected`。前端显示前面人数与已排队时长（`etaSec` 不做）。
2. **互斥串行**：同一账号绝不被两个租约同时占用；账号内严格 `setAlias→收码/超时→释放→下一个`。
3. **唯一码定向**：`gh-` 前缀的码只能用允许分组的邮箱、只收目标发件人的码；前缀错/过期/用尽各返回正确错误码。
4. **超时释放与重申请**：15 分钟无码自动释放；未成功收码的码可重新获取邮箱并成功收码（配额仅成功才扣）。
5. **Web 实时**：页面正确显示别名、倒计时，并经 SSE 实时回显**收到的整封邮件**（验证码由用户自行从邮件查看）。
6. **自用 API**：`POST /leases`→取码（轮询或 webhook）全链路跑通，可被 `register-factory` 集成。
7. **可恢复**：进程重启后占用关系、按需重连 IMAP、未决租约正确恢复或按超时处置。
8. **安全**：全链路日志无任何明文凭据/cookie；唯一码不可枚举。
9. **【头号】杜绝一码多码（FR-0）**——以下竞态用例必须全部通过：
   - ①同码并发 10 次 `activate` → 只产生 **1** 个活跃租约；
   - ②一封验证码邮件被重复投递/IMAP 事件触发两次 → 只交付 **1** 次、配额只扣 **1**；
   - ③超时重申请后旧别名迟到来码 → 旧租约**不交付**、配额**不扣**；
   - ④两封邮件几乎同时命中 quota=1 的码 → 仅 **1** 封被交付，`quota_left` 落到 0 不为负；
   - ⑤进程在「码已收、配额已扣」后崩溃重启 → 该码状态仍为 `used`，**不会再发码**；
   - ⑥绕过应用直接并发写库制造两个 active 租约 → 被 DB partial unique index 拒绝。
10. **多大学差异隔离**：新增一所大学仅新增 `provider/<school>/` 实现 + 配置即可接入，**不改调度核心/FR-0/API/前端**（§0.2/§0.3）。
11. **收码结果回看与保留**：成功收码后，保留期（默认 7 天）内同码再次进入能看到**历史邮件原文**且**不新建租约、不再扣配额**；超 7 天进入提示「**无效的唯一码**」，且过期数据被 GC 清理（FR-2.7/2.8/FR-10）。

## 13. 风险

- **R-1 容量天花板**：并发上限=账号数，且账号内串行（C-1/C-2）。高峰靠加账号/排队缓解，需在售卖侧控制超售。
- **R-2 别名切换的尾部邮件**：账号复用后，发往旧别名的迟到邮件可能落到新租约——靠 C-4 的 `since≥startTime` + `To=新别名` 严格隔离。
- **R-3 单账号会话/cookie 时效**：失效频繁会推高重登频率（已由 swpu-session 自愈 + single-flight 缓解）。
- **R-4 IMAP 连接稳定性**：按需连仅在租约存活期内；期内断线需健壮重连（指数退避），连续失败置 `unhealthy`（FR-1.2）、释放即复位；建连失败回滚本次申请（`RECEIVER_UNAVAILABLE`）。
- **R-5 风控**：别名 HTTP 与浏览器环境不一致可能触发风控（NFR-8 缓解，必要时升级 L2）。
- **R-6 滥用**：唯一码被分享/刷量——靠随机码 + 限流 + `maxRenews` + 单活跃租约约束。
- **R-7 各校登录脆弱**：登录/重登是最易碎环节（验证码改版、表单调整、风控升级），且**各校实现独立**。缓解：登录隔离在各 `provider.login()` 内、失败不影响其它账号；账号转 `unhealthy` 不参与分配（FR-1.2）并告警；调度核心与浏览器解耦（§0.1），单校登录坏不拖垮全局。
- **R-8 一码多码（已重点封堵）**：见 §6 FR-0——DB partial unique index + 单写原子事务 + 收码幂等 + 终态不可逆多重护栏；上线前必须跑通 §12 验收 #9 全部竞态用例。

## 14. 开放问题 / 本次完善所做的关键假设（请你确认）

> 以下是我在草稿基础上**替你做的默认决策**，便于你直接拍板或修正：

1. **「使用掉」= 成功收到一封匹配邮件**（`RECEIVED` 才扣配额，与能否提取出验证码无关）；超时/取消不算使用，可重申请。默认 `quota=1`。是否需要支持「一码多次收码」？
2. **TTL=15 分钟**（来自草稿）为租约「无码」上限，可按套餐配置；另设 `codeValidSec`（码自购买起的整体有效期）与 `maxRenews`（最多重申请次数）。这两个值的默认是多少？
3. **排队而非直接失败**：池满时进入分组队列并返回可见位次（`queueAhead/position`），等待上限 `acquireTimeout` 默认 **60s**，超时才 `POOL_BUSY`。等待上限取多少？是否需要 `etaSec` 预估等待（按近期平均收码时延估算）？
4. **支付在系统外，唯一码预生成发放**（首版不接支付）。是否正确？
5. **多大学通过 `EmailProvider` 接口接入，SWPU 为首个实现**；前缀(套餐)绑定「允许账号分组」。是否需要更细到「按单个账号」绑定？
6. **【本轮已定】技术栈**：`fastify` + `better-sqlite3` + **单实例、不引入 Redis**（理由见 §10.5），队列/锁走进程内存并以 `QueuePort`/`LockPort` 预留 Redis 升级路径；Docker 单容器 + `data/` volume。若你预期**未来必然多实例**，可提前改用 Postgres + Redis——请确认是否需要。
7. **实时回显用 SSE**（回退轮询）。是否接受，还是要 WebSocket？
